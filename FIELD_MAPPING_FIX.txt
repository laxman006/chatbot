====================================================================================================
 CRITICAL BUG FIX - FIELD NAME MISMATCH CAUSING 100% VALIDATION FAILURE
====================================================================================================

ISSUE IDENTIFIED:
- OpenAPI extracted 174 Slack endpoints ✅
- But ALL 174 endpoints failed validation ❌
- Root cause: FIELD NAME MISMATCH between OpenAPI parser and normalizer

====================================================================================================
 THE BUG
====================================================================================================

OpenAPI Parser creates endpoints with these fields:
{
    "method": "POST",
    "path": "/users.list",                    ← Uses 'path'
    "operation_name": "users.list",            ← Uses 'operation_name'
    "description": "List all users",
    "source": "openapi"
}

But Cloud API Researcher tried to access:
{
    ep["endpoint"]          ← WRONG! Should be ep["path"]
    ep["vendor_operation"]  ← WRONG! Should be ep["operation_name"]
}

This caused KeyError or empty string access, which made ALL endpoints fail validation!

====================================================================================================
 LOCATIONS OF THE BUG
====================================================================================================

FILE: app/cloud_api_researcher.py

1. Line ~415: Logging rejected endpoints
   BEFORE: logger.debug(f"... {ep['endpoint']} ...")
   AFTER:  path = ep.get('path', ep.get('endpoint', 'N/A'))

2. Lines ~428-437: Calling normalizer
   BEFORE: vendor_operation=ep["vendor_operation"], endpoint=ep["endpoint"]
   AFTER:  vendor_op = ep.get("operation_name", ep.get("vendor_operation", ""))
           endpoint_path = ep.get("path", ep.get("endpoint", ""))

3. Line ~447: Logging rejected mappings
   BEFORE: logger.warning(f"... {ep['endpoint']} ...")
   AFTER:  ep_path = ep.get('path', ep.get('endpoint', 'N/A'))

4. Lines ~468-472: Creating operation data
   BEFORE: ep["vendor_operation"], ep["endpoint"], ep["description"]
   AFTER:  vendor_op, endpoint_path, ep.get("description", "")

====================================================================================================
 WHY TWO DIFFERENT FIELD NAMES?
====================================================================================================

The system has TWO extraction methods:

1. OpenAPI Parser (NEW, PRIMARY)
   - Parses machine-readable OpenAPI/Swagger specs
   - Creates: 'path', 'operation_name'
   - Example: Okta, Slack, GitHub OpenAPI specs

2. HTML Scraper (FALLBACK, LEGACY)
   - Scrapes HTML documentation
   - Creates: 'endpoint', 'vendor_operation'
   - Example: Custom cloud docs

The researcher MUST support BOTH!

====================================================================================================
 THE FIX - FIELD-AGNOSTIC ACCESS
====================================================================================================

STRATEGY: Use .get() with fallback to support both field name conventions

✅ For endpoint path:
   endpoint_path = ep.get("path", ep.get("endpoint", ""))

✅ For operation name:
   vendor_op = ep.get("operation_name", ep.get("vendor_operation", ""))

✅ For description:
   description = ep.get("description", "")

✅ For source URL:
   source_url = ep.get("source_url", "")

This allows the system to work with:
- OpenAPI-extracted endpoints (path, operation_name)
- HTML-scraped endpoints (endpoint, vendor_operation)
- Any future extraction methods
